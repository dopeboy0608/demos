# ARCHITECTURE

> CLAUDE.md가 참조하는 기준들(테스트 하네스 적용 기준, 작업 분기 기준)을 담는다. 기준이 바뀌면 이
> 파일을 먼저 수정하고, CLAUDE.md나 스킬 파일에는 기준을 복사해 넣지 않는다.

## 현재 구현 범위

개인용 데모/실험 프로젝트. 프론트엔드 UI만 구현하며 백엔드/DB는 두지 않는다. 로그인/인증, DB/백엔드
API, 결제 등 백엔드가 필요한 기능은 현재 범위 밖이며 별도 논의 없이 구현하지 않는다.

## 구조 개요

도메인 전용 코드는 `src/features/<domain>/{api,components,hooks,queries,helper}`에 두고, 공용
코드는 `src/{api,components,config,pages,routes}`에 둔다. 테스트 공용 설정과 MSW 핸들러는
`src/test/`에 둔다. 자세한 레이아웃은 [CLAUDE.md "디렉터리 구조"](../CLAUDE.md#디렉터리-구조) 참고.

## TDD 적용 기준

- **TDD 대상**: 입출력이 명확하고 부수효과 없는 순수 함수. 테스트를 먼저 쓰고 구현한다.
  - 예: 외부 API 응답을 내부 모델로 변환하는 함수, 좌표/단위 변환 함수 등 — 입력과 기대 출력이
    고정되어 있고 네트워크나 DOM 의존이 없는 로직.
- **TDD 대상이 아닌 것**: UI 컴포넌트, 부수효과 중심 훅, HTTP 인터셉터 등 외부 상태/환경에 의존하는
  코드. 기대 동작은 요청이나 이슈 내용으로 먼저 명확히 하고, 필요하면 이후 통합/컴포넌트 테스트로
  검증한다.

## 작업 분기 기준

`issue-start`가 아래 신호를 적용해 두 경로 중 하나를 추천하고 사용자에게 확인받는다. 추천은
힌트일 뿐이며 최종 결정은 사용자가 한다.

- **큰 작업** (전략 스킬 사용): 요구사항이 모호해 먼저 조사가 필요하거나 / 범위가 커서 여러
  서브태스크로 나눠야 하거나 / 설계 비중이 크고 사용자 판단이 필요한 결정 지점이 있는 경우.
- **작은 작업** (바로 구현): 원인과 해결 방법이 이미 명확한 버그 / 기존 패턴을 따르는 1~2개 파일
  수준의 작업 / 별도 조사가 필요 없는 경우.
- 이슈가 두 신호를 동시에 가지면, 이슈의 핵심 리스크에 더 가까운 신호를 기준으로 판단하고 이유를
  짧게 설명한다.
- 두 경로 모두 CLAUDE.md의 이슈/브랜치 컨벤션을 따르며, 커밋/PR/머지는 CLAUDE.md의 전략 규칙에서
  달리 명시하지 않는 한 사용자가 명시적으로 요청할 때만 진행한다.

## 외부 SDK 모킹 전략

`<script>` 태그를 주입하거나 네트워크로 비동기 로딩되는 SDK(지도, 결제, 에디터 등)는 jsdom 같은
테스트 환경에서 로딩이 끝나지 않거나 전역 객체가 정의되지 않는다. 테스트 대상별 접근:

- **순수 로직 테스트**: 실제 SDK를 흉내낼 필요 없이, 코드가 실제로 사용하는 API만 구현한 최소
  모킹 객체를 전역에 꽂아 넣는다. 필요한 API만 그때그때 추가한다(SDK 전체를 재현하지 않음).
- **컴포넌트 테스트**: 모듈 모킹(`vi.mock` 등)으로 초기화 훅이 즉시 준비 완료 상태를 반환하게
  하고, SDK가 제공하는 컴포넌트는 단언하기 쉬운 단순 컴포넌트로 대체한다.

이 프로젝트에서는 `react-kakao-maps-sdk`(카카오맵)가 이 전략의 대상이다. 전용 모킹 파일은 아직
없으므로, 지도 관련 컴포넌트/훅을 테스트할 때 위 전략에 따라 그때 만든다.
