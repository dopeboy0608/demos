## TDD 적용 기준

아래 기준으로 TDD 적용 대상을 구분한다.

- **TDD 대상**: 입출력이 명확하고 부수효과가 없는 순수 함수. 테스트를 먼저 쓰고 구현한다.
  - 대표 사례: 외부 API 응답을 내부 모델로 변환하는 함수, 좌표/단위 변환 함수처럼 입력과 기대 출력이
    고정돼 있고 네트워크·DOM 의존이 없는 로직.
- **TDD 대상 아님**: React 컴포넌트, 커스텀 훅(geolocation 등 부수효과 중심), axios 인터셉터처럼 외부
  상태·환경에 의존하는 코드. 이런 코드는 `docs/spec/`(SDD 템플릿)으로 먼저 스펙을 정리하고, 필요 시
  사후에 통합/컴포넌트 테스트로 검증한다.

## spec-kit 적용 기준

이슈 작업을 시작할 때 `issue-start` 스킬(`.claude/skills/issue-start/`)로 진입하며, 이 스킬이 아래
기준에 따라 두 시나리오 중 하나를 추천하고 사용자 확인을 받는다. 최종 판단은 항상 사용자가 내린다 —
아래는 추천 근거일 뿐 강제 규칙이 아니다.

- **spec-kit 적용 추천**: 요구사항에 모호함이 있거나 데이터 소스/API 조사가 선행돼야 함 / 여러 User
  Story로 쪼갤 만큼 범위가 큼 / 그룹 분류·우선순위 등 사용자 판단이 필요한 분기점이 예상됨.
  - `issue-start`가 이 경로를 추천하면 `speckit-start` 스킬(`.claude/skills/speckit-start/`)을 호출해
    `/speckit-specify` → (필요 시 `/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks` →
    `/speckit-implement`를 단계별로 진행하며, 각 단계 완료 후 다음 단계로 넘어가기 전 사용자 확인을
    받는다.
- **기존 방식(바로 구현) 추천**: 원인과 해결책이 이미 명확한 버그 / 1~2개 파일, 기존 패턴을 그대로
  따르는 작업 / 조사할 거리가 없음.
  - 이 경로에서는 spec-kit 없이 브랜치 생성 → 구현 → 테스트/포맷/린트 → (사용자 요청 시) 커밋/PR로
    바로 진행한다.
- 두 경로 모두 브랜치/`in-progress` 라벨 부여 등 [GitHub 이슈 관리](../CLAUDE.md#github-이슈-관리) 공통
  규칙을 따르며, 커밋/PR/머지는 기존과 동일하게 사용자의 명시적 요청이 있을 때만 진행한다.
- `issue-start`/`speckit-start` 두 스킬은 트라이얼 단계로 들여온 것이다 — 프로젝트마다 신호(모호함,
  범위, 조사 필요성)의 기준이 다를 수 있으니, 실제로 몇 번 써보면서 이 기준을 프로젝트에 맞게
  구체화하는 걸 권장한다.

## 외부 SDK 모킹 전략

지도, 결제, 에디터 등 실제로 `<script>` 태그를 주입하거나 네트워크로 비동기 로딩되는 SDK는 jsdom 같은
테스트 환경에서 그대로 두면 로딩이 끝나지 않거나 전역 객체가 존재하지 않는다. 테스트 대상에 따라 다르게
접근하는 걸 권장한다.

- **순수 로직 테스트**: 실제 SDK를 흉내낼 필요 없이, 테스트 대상이 실제로 쓰는 API만 최소로 구현한
  목을 전역에 심는다. 새 API가 필요해지면 그만큼만 추가한다(SDK 전체 재현 금지).
- **컴포넌트 테스트**: 모듈 모킹(`vi.mock` 등)으로 초기화 훅이 즉시 완료 상태를 반환하게 하고, SDK가
  제공하는 컴포넌트는 테스트에서 검증하기 쉬운 단순 컴포넌트로 대체한다.

[이 프로젝트가 실제로 쓰는 SDK가 있다면 여기에 구체적인 모킹 파일 경로/함수명을 적는다.]
