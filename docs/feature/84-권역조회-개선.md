## 결정 로그

- **경기 데이터 소스**: `cubensys/Korea_District`(#64와 동일 저장소, 라이선스 미명시 —
  비상업 개인 데모 프로젝트 한정 사용을 사용자가 재확인). 전국 기초자치단체 경계
  (`2_대한민국_기초자치단체_경계_2017.geojson`)에서 행정코드 `41`(경기도) 42개 시/군/구를
  추출.
- **경기 소분류/세분류**: 이 저장소에는 경기도 읍면동 단위 경계가 없다(시/군/구 단위까지만
  존재, 조사로 확인). 서울처럼 실제 동 경계를 쓸 수 없어, 시/군/구 외곽 경계 자체를
  `radialSubdivision.createAreaDivisionsFromRing`으로 재귀 분할(소분류 → 다시 세분류)해
  시뮬레이션한다(`buildGyeonggiDistrictDerived`, regionViewApi.ts).
- **경기 지오메트리 단순화**: cubensys 원본 시/군/구 경계가 평균 4천 점/구로 매우 촘촘해
  42개 전체가 4.5MB에 달했다. `shapely.simplify(0.0005도, preserve_topology=True)` 적용 시
  면적 변화가 사실상 0(최대 상대 오차 ~1e-14, 중복·거의 직선인 점만 제거됨)임을 확인하고
  적용 — 228KB로 축소(서울 195KB와 비슷한 수준).
- **서비스유형 매핑**: 기존에는 서울 25개 구를 인덱스 홀짝으로 샛별/하루 배송에 번갈아
  배정했다. #84 요구사항에 따라 서울=샛별배송(DAWN) 전용, 경기=하루배송(DAY) 전용으로
  고정.
- **절차적 가상센터(A~Z, 21개) 비노출**: 완전 삭제 대신 `TEMP_REGION_GROUP_OPTIONS`(검색
  조건 UI가 쓰는 목록)에서만 제외했다. `REGION_GROUP_PROFILES`(데이터 레이어)는 그대로
  유지해 롤백이 쉽다.
- **줌레벨 조건**: `ZOOM_LEVEL_REGION_MIN` 6→5로 변경. 소분류 5~7, 세분류 4 이하로 표기
  (요구사항의 "6레벨부터 소분류, 4레벨부터 세분류"를 만족).
- **폴리곤(2레벨) 적용(FR-08)**: cubensys에도 지번/우편번호 블록 단위 데이터가 없음을
  확인 → 적용 보류, 세분류까지만 유지. 코드 변경 없음.
- **배송센터 기본 전체 선택**: 서비스유형 전환 시에도 전체 선택 기본값을 유지하도록
  구현(전환마다 다시 전체 선택 버튼을 눌러야 하는 불편을 피함).

## 조사 결과(Phase B 팩트파인딩)

- 서울 구 센터는 `profile.name`이 `SEOUL_DONGS_BY_GU`에 키로 존재하는지로 구분해
  `buildSeoulDistrictDerived`로 라우팅한다. 경기 센터는 `profile.name`이 있지만
  `SEOUL_DONGS_BY_GU`에는 없으므로 `buildGyeonggiDistrictDerived`로 라우팅 — 기존
  분기 조건(`profile.name && profile.coordinates`)만으로는 서울/경기를 구분할 수 없어
  분기를 2단계로 나눴다.
- 지도 기본(센터) 레벨 폴리곤(`MOCK_POLYGONS`)은 서울/경기 모두 `profile.coordinates`를
  그대로 쓰므로 수정이 필요 없었다(기존 조건이 이미 "name && coordinates 있으면 실경계"였음).
- 크로스체크 게이트: 디자인 파일 없음(n/a), 코드 교차검증 결과 01~02를 막는 ①/② 항목
  없음(게이트 통과). ③(스펙-코드 불일치) 항목은 모두 질문 라운드에서 해소(경기 데이터
  소스/대상 범위/폴리곤 보류).
