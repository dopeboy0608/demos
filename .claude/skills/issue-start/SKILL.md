# issue-start

이슈가 등록된 뒤의 표준 진입점. 작업 분기 기준은 [docs/ARCHITECTURE.md "작업 분기 기준"](../../../docs/ARCHITECTURE.md#작업-분기-기준)에 있으며, 이 스킬은 그 기준을 적용만 한다. 기준이 바뀌면 ARCHITECTURE.md를 먼저 수정한다.

## 절차

1. **이슈 번호**: `$ARGUMENTS`에 번호가 없으면 사용자에게 물어본다.
2. **이슈 읽기**: `gh issue view <N> --json number,title,body,labels,state` 명령으로 제목, 본문,
   라벨을 읽는다. 이 값을 이슈 번호/제목/본문 요약 형태로 전략 스킬에 넘길 수 있게 준비한다.
3. **판단**: "작업 분기 기준"의 신호를 이슈에 적용해 하나를 추천한다.
   - **A. 작은 작업** (바로 구현)
   - **B. 큰 작업** (전략 스킬)
   - 이슈가 두 신호를 동시에 가지면, 핵심 리스크에 더 가까운 신호로 판단하고 이유를 짧게 설명한다.
4. **추천 및 확인**: 이유를 1~2문장으로 설명하고 추천 답을 제시한 뒤, 사용자가 A/B를 직접
   선택하게 한다. 사용자가 다르게 선택하면 그 선택을 따른다 — 추천은 힌트일 뿐이다.
5. **공통 준비** (두 경로 모두), CLAUDE.md "GitHub 이슈 관리"를 따른다:
   - `gh issue edit <N> --add-label in-progress` (먼저 확인받고 실행)
   - 저장소의 기본 브랜치에서 브랜치를 만든다(이 저장소는 기본 브랜치로 `main`을 사용한다):
     `git checkout main && git pull origin main --ff-only` (origin 리모트가 없으면 pull은 건너뜀)
     `&& git checkout -b <타입>/<N>-<설명>`. 타입은 이슈 라벨에서 가져온다(`bug`→`bug/`,
     `feature`→`feature/`, `chore`→`chore/`, `docs`→`docs/`).
   - **경로 A**: 지금 바로 브랜치를 만든다. **경로 B**: 여기서는 브랜치를 만들지 않는다 — 전략
     스킬이 구현 단계에 도달할 때 CLAUDE.md의 전략 규칙에 따라 스토리 브랜치 하나만 만든다.
6. **분기**:
   - **A**: 스킬을 호출하지 않는다. 이 대화에서 이슈 내용을 바탕으로 바로 구현을 시작한다. 이후
     CLAUDE.md "명령어" 섹션의 포맷/린트/테스트 명령을 실행해 통과를 확인한다. 커밋/PR/머지는
     사용자가 명시적으로 요청할 때만 진행한다.
   - **B**: 전략 스킬은 명시 호출 전용(`disable-model-invocation`)이므로 Skill 도구로
     `feature-strategy`를 호출할 수 없고 그 절차를 흉내내서도 안 된다. 대신 핸드오프한다: 사용자가
     승인한 공통 준비를 마친 뒤, 이슈 번호·제목·본문 요약과 이미 알고 있는 사실(기존 서브이슈,
     목/API 상태 등)을 담아 바로 붙여넣을 수 있는 명령 한 줄을 출력한다. 예:
     `/feature-strategy Issue #24: <제목> — <본문 요약>`. 플러그인 설치 형태에서는
     `/dopeboy0608-skills:feature-strategy`로 호출한다고 안내하고, 라벨/브랜치 작업은 이미 끝났다고
     알려준다. 사용자가 명령을 찾을 수 없다고 하면 `ai-workflow-setup`을 실행하라고 안내하고(이
     스킬이 플러그인 설치 여부를 확인한다) 중단한다.

## 하지 않는 것

- 커밋, PR 생성, 머지를 스스로 하지 않는다 — 항상 사용자의 요청을 기다린다.
- 작업 분기 기준 자체를 이 파일에 나열하지 않는다 — ARCHITECTURE.md가 단일 출처다.
